# Runnable examples

## Shared capabilities

The common documentation environment includes core Ranvier, Ranvier.View, motion bindings and typed CSS. The central host registers the shared Ranvier example plugin and Nacara's live editor. Source repositories inherit those capabilities through the host; their normal library projects do not acquire documentation-only runtime dependencies.

Three fence families have different purposes:

- `fsharp ranvier` compiles a component, renders initial HTML at build time and hydrates it in the browser.
- `fsharp map` renders an interactive signal-map scenario with its controls and trace data.
- `fsharp live` provides an editable F# example compiled and evaluated in the browser.

An ordinary `fsharp` fence remains a highlighted code listing. It does not implicitly become a runnable application.

The [shared runnable showcase](runnable-examples.md) exercises these capabilities with real rendered examples rather than displayed syntax alone.

## Render a component

Use an expression whose value is a `Component<unit>`:

````markdown
```fsharp ranvier
MyExamples.counter
```
````

Expose reusable samples in a referenced example module. The plugin compiles the page and produces a browser entry point; it also evaluates the example for SSR. A reader sees initial content before JavaScript loads, then hydration attaches reactive behaviour.

To declare a named component in the fence, use `render=name`. `setup` fences supply declarations shared by later examples on the same page. Keep setup self-contained and avoid hidden dependencies on another documentation page.

## Display options

The default `show=both` displays code and output. `show=output` displays only the preview; `show=code` displays the source; `show=inline` uses the plugin's inline presentation. `id=counter` assigns a stable host id within the page. Use unique ids.

````markdown
```fsharp ranvier show=output id=counter
MyExamples.counter
```
````

Backtick and tilde fences are supported. Invalid options, duplicate ids and unclosed fences produce source-line diagnostics. For a documentation page teaching this syntax, wrap the example in a longer outer fence, as this guide does, so the inner example stays a displayed sample.

## Add repository-specific sample modules

Create a small `.fsproj` containing the sample modules and set the manifest:

```json
{
  "version": 1,
  "examplesProject": "docs/samples/Forms.Examples.fsproj"
}
```

Use ordinary NuGet or project references inside that `.fsproj` for its .NET dependencies. The host generates `.generated/Examples.fsproj` referencing the shared preset and each imported repository's extra sample project. The additional project extends the environment rather than replacing it.

Keep sample module names distinct across repositories, for example `Ranvier.Forms.Docs.Examples`, so pages can refer to an unambiguous module. Do not rely on compilation order between different repositories' sample projects. A sample project's relative project references must resolve inside the acquired/local layout; use the documented coordinated roots for cross-repository references.

## Literate F# helpers

For a new literate `.fsx` page, keep loadable support modules inside its configured content tree, for example `_support/Helpers.fs`, and use a relative `#load`. The importer copies `.fs` support files without treating them as documentation pages. Keep the support module valid for F# file loading and avoid developer-machine absolute paths.

The importer only transforms Markdown links inside literate documentation comments; executable F# and string literals remain unchanged. The central build also provides a generated compatibility helper for the core docs' established `#load "../../literate.fsx"` pattern, using centrally built preset dependencies. That helper is generated by the build infrastructure; do not edit it as a source fix.

For a literate page one folder below a source's content root, such as `docs/content/guide/signals.fsx`, the central helper is two directories above the staged page. A complete page skeleton is:

```fsharp
(**
---
title: Signals in a literate page
---

# Signals
*)

(*** hide ***)
#load "../../literate.fsx"

open Ranvier

(*** show ***)
let count = createSignal 0

(**
Writing the signal changes its current value.
*)
count.Value <- 1
```

Adjust the relative helper path if the page is at a different depth. Keep front matter inside its literate documentation comment; raw YAML before F# code is not valid F# source. A library can instead load its own content-local `.fs` helper when it needs extra definitions. Central example project extensions are the normal way to add extra library references to the preset.

The core, View and CSS roots are exposed to the build as `RanvierRoot`, `RanvierViewRoot` and `RanvierCssRoot`. The build resolves these from the actual selected source checkouts. Avoid absolute developer-machine paths in checked-in sample projects.

## Motion examples

Use the shared animation packages for a small component demonstration. Browser-side motion libraries are bundled with the component entries; .NET-side example rendering must still be valid without a browser animation engine. Use the established motion APIs and SSR-safe setup patterns from the View documentation.

The default runtime npm package is `animejs` version `4.5.0`. If a repository needs another browser package, declare it explicitly:

```json
{ "version": 1, "packages": [["some-runtime", "1.2.3"]] }
```

`packages` is for npm runtime bundling. It does not add a NuGet dependency. Different requested versions for the same runtime package are rejected; coordinate a shared version instead of letting import order select one.

## Typed CSS examples

The preset supplies typed CSS modules. A component can demonstrate declarations, rules and reactive integration through the same example pipeline. Keep CSS selectors scoped to the example host when a rule might otherwise affect the documentation shell.

Changes to the shared documentation theme belong in the theme project, where styles are authored with Ranvier.Css. Avoid using example CSS as a hidden way to restyle every page in a repository.

## Signal maps

Map fences use `Ranvier.Docs.Maps` from the shared environment. The imported map authoring/model/runtime infrastructure preserves the original scenario compilation and graph controls. Trace-enabled compilation is required; the central docs build sets the trace property for the shared projects and generated examples.

Map scenarios may share setup within their page. Keep graph ownership and cleanup explicit. A map shows the reactive graph's behaviour, while a component preview shows its rendered UI; choose the form that explains the concept.

## Editable live examples

Live fences use the common editor preset. Their source must explicitly mount its component into the editor's output host, following the actual shared live example fixture. Build-rendered component fences have a generated entry point; an editable snippet has a different lifecycle and must not assume that entry point exists.

The live editor supplies precompiled project modules and checker metadata. The host registers Xantham metadata needed for DOM bindings, including signature resources. Keep those versions coordinated with the preset and Fable compiler.

The maintained metadata hook also prepares compressed signature/optimisation resources in the precompiled checker assembly. This preserves assembly identity, types and resource contents while moving that preparation out of the browser's first check. The first run still initialises the checker; later edits reuse it.

The generated live output template maps the pinned Anime.js runtime to locally served modules, with its license retained alongside them. Core maps and motion therefore work in edited previews without an external animation CDN. For a new npm package, `packages` supplies rendered-example bundling; browser-edited code also needs a corresponding browser-resolvable import in the maintained live template/runtime adapter. Do not assume an arbitrary .NET reference or bare npm import becomes available in the standalone browser compiler automatically.

Packages requiring a compiler plugin are not automatically supported by browser standalone compilation. In particular, `Ranvier.View.Arms` and compiler-plugin-dependent forms need a local project build. Use a precompiled rendered example or displayed source for that material; do not promise editable compilation for forms the standalone compiler cannot execute.

## What to test

Run the complete plugin/map tests for scanner and generated-workspace changes. Build the site to compile and render actual scenarios. In the browser, verify that SSR content exists before interaction, hydration updates the same example, motion can be started, and a supported live snippet compiles and mounts after editing.

Keep at least one representative component, map, motion example and live example as shared fixtures. The complete build must exercise the dependencies used by actual source pages, rather than only type-check an empty preset project.

## Common failures

An unknown module usually means the sample project is not referenced or the code uses the wrong namespace. An npm resolution error usually means a runtime package is absent or conflicting. A server-rendering error may indicate browser-only setup at module initialisation. A browser checker error can be metadata or a compiler-plugin limitation. Use [Troubleshooting](troubleshooting.md) to distinguish them before changing the example API.
